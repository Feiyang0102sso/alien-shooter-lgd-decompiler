# LGC 拆分与合并去重方法论 (LGC Split & Merge Methodology)

在 LGD 反编译工具的开发中，将编译后的单一巨大 `.lgc` 代码还原为模块化的多物理文件，并对多个源文件进行“同类项合并去重”，是保证代码可读性、可维护性以及二次顺利编译的灵魂所在。

本篇方法论系统阐述了 `lgd_tool` 进行 LGC 大文件拆分与多文件合并的理论基础与物理实施方案。

---

## 1. 核心拆分方法论 (Split Methodology)

反编译直接产出的 `.lgc` 是一个包含全局变量、内置声明以及数百个函数的单一巨型文本。我们采用**“头部三分法”**和**“函数行号回跳切段”**的双轨制拆分策略。

### 1.1 头部三分法
在巨型 `.lgc` 的开头，内容被严格分流：
1. **引擎 API 声明段 (`extern`)**：
   - 提取所有以 `extern` 开头的语句。
   - 物理分流写入唯一的 `core/export.lgc` 文件。
2. **宏定义段 (`#define`)**：
   - 当启用 `--refine` 选项时，由常量数据库对硬编码数值进行恢复，写入 `core/export.lgc` 头部。
3. **全局变量声明段 (`globals`)**：
   - 提取所有位于头部、以 `int` 或 `string` 开头的全局变量定义。
   - 通过跨文件的一致性比对，分流进入公共区或本地注入区。

### 1.2 函数行号回跳切段 (Segment by Line Jumps)
LGC 编译器采用“先定义、后调用”的物理排版规则，且同源文件在编译为二进制时，指令对应的原始行号注释是严格单调递增的。
- **切段核心算法**：
  $$\text{If } \text{next\_function}.\min\_line < \text{prev\_function}.\max\_line \implies \text{触发切段 (New Segment)}$$
- **回跳规则解析**：
  1. 依次遍历解出物理顶层函数列表，并解析出每个函数体内出现的最小行号（`min_line`）和最大行号（`max_line`）。
  2. 保持函数在文件中的物理出现顺序，当前函数的 `min_line` 小于上一有效函数的 `max_line` 时，说明发生了行号“回跳”，判定原项目在这里引用了另一个新的包含源文件（`#include` 边界）。
  3. **第一个段**（第一次回跳前发生的所有方法）默认并入 `export` 公共段。
  4. **最后一个段**即使包含 `main()`，也不盲目将其视为主地图脚本，主脚本由 manifest / 物理路径指定。

## 2. 核心合并去重方法论 (Merge & Deduplication)

当面临多个源文件（例如多个关卡 LGC）的联合反编译重构时，我们需要做“合并同类项”。我们遵循以下严苛的去重与冲突隔离原则。

### 2.1 Export 强一致校验与熔断
- **原则**：**不进行排序**。必须保持物理上的原始声明行顺序。
- **细节**：如果不同文件里的 `extern` 声明行数不同、内容不符或顺序错乱，直接调用 `logger.error` 详细打印出第几行的文本冲突，且**直接调用 `sys.exit(1)` 强行终止进程**。说明这根本不是同一套反编译工程，直接予以程序熔断。

### 2.2 Global 变量的差异化分发与局部注入
- **原则**：编译器禁止重定义。对于在不同大文件中表现出差异的全局变量，采取“局部降级保留”策略。
- **细节**：
  1. **公共变量**：在所有大文件中都出现，且定义文本 100% 一致。写入公共 `core/global_variable.lgc`。
  2. **冲突/独占变量**：定义文字存在不一致或仅为个别大文件独占。**使用 `logger.warning` 提醒用户注意**，但不终止进程。
  3. **局部注入**：将这些特异变量**直接注入到所属大文件拆分出的最后一个段脚本（即它的主入口脚本，如 `level_01.lgc`）的物理最开头**。作为本脚本的局部定义存在，既消除了重定义冲突，又最符合入口脚本的物理常理。

### 2.3 普通代码段（Segment）的内容哈希段池（Segment Pool）
- **核心痛点**：引用顺序解耦。`fileA` 的第 10 份普通段和 `fileB` 的第 2 份普通段在内容上是完全相同的。我们不能依赖“物理顺序匹配”。
- **方案**：
  1. 在内存中将段内所有函数的代码进行完整拼接（统一换行符），计算其 **MD5 内容指纹**。
  2. 建立一个全局哈希池。新哈希则分配唯一物理名写入磁盘（如 `segment_01.lgc`。若物理文件名已被占用，则动态加后缀如 `segment_01_001.lgc` 保证安全写入）。
  3. 遇重复哈希（同类项），**直接抛弃写盘，并复用已有的物理文件名**。
  4. 记录各文件对这些物理段的**有序引用链**，在生成 `#include` 时进行还原。如此完美解决乱序比对和空间物理去重！

我们目前用到的对比方式，以及之前讨论过的其他对比方式，主要在**比对维度（内存还是物理文件）**与**一致性容忍度（原物理顺序还是无序哈希）**上有着本质的区别。

以下为您做清晰明了的盘点：

---

### 一、 目前实际用到的比对方式：
#### 【内存级原物理顺序逐行精确比对】 (Line-by-Line Exact String Comparison)
* **应用位置**：目前我们在 `merger.py` 中针对 **Export** 所实现的核心比对方式。
* **物理实现逻辑**：
  1. **不进行排序**，直接将不同大文件提取出的 `extern` 声明行，去除首尾空白并压缩多余连续空格，按原始行数进行物理位置的一一对应。
  2. 优先比对总行数。如果行数不同，直接通过 `logger.error` 详细报错并 `sys.exit(1)`。
  3. 若行数相等，按照物理位置索引 `idx` 逐行精确执行 `base_line != other_line` 比对。**只要有任何一行的内容不一致、或内容一样但顺序前后颠倒了，直接熔断强退**。
* **特点**：极度严苛。对“物理顺序”和“行内容”进行双重绝对锁定，差一个字节或顺序不一致都无法通过。

---

### 二、 之前讨论过的其他比对方式（共有三种）：

#### 方式 B：【内存级文本 MD5 内容指纹比对】 (Content Hashing Comparison)
* **讨论场景**：针对 **一般代码段（Segment）** 的合并去重。
* **物理实现逻辑**：
  1. 不同的文件引用的公共代码段顺序是完全错乱的（例如 `fileA` 在第 10 份载入，`fileB` 在第 2 份载入），我们无法像 Export 那样进行原序行比对。
  2. 因此，我们在内存中将一个普通段内所有的函数代码文本进行大拼接（统一换行符），计算其唯一的 **MD5 哈希值**。
  3. 维护一个全局段池 `global_segment_pool`。只要当前切出的段 MD5 在池中已存在，说明内容完全一致。物理上**立刻抛弃写盘**，并复用已有的物理文件名。
* **特点**：**彻底解耦了引用的物理顺序**。它是通过“指纹”判定内容是否 100% 相同，从而完成跨文件乱序匹配去重。

#### 方式 C：【物理文件级二进制比对】 (File-Level Binary Comparison)
* **讨论场景**：针对要在**物理磁盘层面**，精确验证两个文件内容是否 100% 相同（差一个字节都不行）的场景。
* **物理实现逻辑**：
  1. 调用 Python 底层高度优化的 `filecmp.cmp(file1, file2, shallow=False)`。
  2. 它会优先读取文件的物理属性大小（`stat().st_size`），如果文件字节大小不相等，微秒级判定不同。
  3. 如果大小相同，它会分块缓冲对比，在字节级别验证是否 100% 完全一致。
* **特点**：速度极快，是 Python 最权威的**物理磁盘文件去重手段**，不需要写繁复的循环读行比对逻辑。

#### 方式 D：【内存级无序集合去重比对】 (Set-based Comparison)
* **讨论场景**：我们在二次升级 Export 规则前探讨过的临时方案（后来已被当前的原序严苛比对所取代）。
* **物理实现逻辑**：
  1. 将所有提取出的 `extern` 声明行清洗后放入 `set`（集合）中，自动去除重复，并不限制顺序。
  2. 对比两个文件的 export 集合是否完全相等（或求差集），看是否有漏掉或多余的 API。
* **特点**：**允许声明顺序发生乱序改变**。只要包含的 API 签名库内容本身是一致的，即可认为一致。但这无法拦截“行物理顺序不一致”的情形，所以最后我们根据您的要求，放弃了这种无序集合比对，升级为了当前最严苛的**原顺序比对**。

---

通过这四种方法的各司其职（`export` 用**原序行比对**，`global` 用**变量名字典一致性比对**，`segment` 用**内存 MD5 指纹池去重**），我们成功打通了这套反编译重构工具最核心的去重底层逻辑！
