# LGD File Documentation

## Overview

The LGD compiler is an offline static compiler + static linker.

The relationship between LGC and LGD can be analogized to that of a Java source file and a JVM-compiled `.class` file.

It was originally designed for early mobile game platforms. Its purpose is to pre-compile readable C-like scripts (`.lgc`) into machine-executable binary bytecode (`.lgd`) in exchange for faster loading speeds and lower CPU overhead. Encryption is merely an incidental byproduct.

Suppose a level script `Level01.lgc` references 10 external scripts, such as `common.lgc`. Without compilation, the engine would need to simultaneously initiate 10 file I/O operations for reading and parsing when loading the level, which is highly inefficient. However, after using the LGD compiler, all dependencies are packaged and linked into a single independent `.lgd` file. The engine only needs to handle a single I/O operation to complete the loading process, significantly improving execution efficiency.

Its compilation method mainly consists of three parts:

*   **Preprocessing:** Recursively processes `#include` directives in the source code. It "kneads" all referenced common scripts (such as `items.lgc`, `common.lgc`) into a final binary stream, much like linking C code.
*   **Syntax Validation:** Features complete syntax validation capabilities; if there is an error, it will directly report it.
*   **Map Binding Mechanism:** The compilation process uses a `.map` file as an index. It adopts a "one map, one script package" strategy.

## Part 1: Literal Table

It is primarily responsible for recording the status and initial values of all variables -- **(global variables, function parameters, local variables)**.

**The fixed first 4 bytes represent the index count.**

> [!IMPORTANT]
>
> 1. The engine's lowest level actually only supports `int`, `string`, and their corresponding arrays.
> 2. Although you can see the `boolean` type in the scripts, they are essentially `int` at their core. The author used macro definitions to make the scripts look closer to C code.
> 3. Although the engine reserves support for "pointer" operations in the underlying flags, they have never been actually used in official scripts.
> 4. There is no difference in the compiled file between `static` and non-`static` **global variables**; the difference between these two keywords only manifests when they are used as **local variables**.

### 1. Core Concept: The Difference Between Index and Global ID

To understand the Literal Table, you must first clarify the difference between `Index` (Entry Index) and `Global ID` (Global/Logical ID). This is also the most confusing part of the entire table:

- **Index (Entry Index):** Represents a physical storage "slot". A basic variable takes up 1 Index; for an array of length $N$, each of its elements will occupy 1 independent Index. The `Entry Count` at the beginning of the file refers to the total number of Indexes.
- **Global ID (Logical Group ID):** Represents logical "ownership/affiliation". It is assigned in groups:
    - A standard variable exclusively occupies 1 ID.
    - **An entire array, regardless of how many elements it has, shares the same ID.**
    - **A function, along with all its internal parameters and local variables, also entirely shares the same ID.**

**👇 Experimental Comparison: Array Index vs. ID Allocation**

Let's take an `int` array with 3 elements as an example:

```c++
int intArray[3] = { 114, 514, 19198 };
```

In the Literal Table, it is split into 3 Index entries, but they share the same ID (for example, ID is `9`). Please observe the difference between the first array item and the subsequent items:

```c++
// [GlobalID: 9] Occupies 3 Index entries
// Flag | String (Empty) | Size or ID          | Value
   8E     00          03 00 00 00 /* Size: 3 */    72 00 00 00 /* Val: 114 */
   8E     00          09 00 00 00 /* ID: 9   */    02 02 00 00 /* Val: 514 */
   8E     00          09 00 00 00 /* ID: 9   */    FE 4A 00 00 /* Val: 19198 */
```

> [!TIP]
> The first Index entry of the array records the **total length of the array (Size)**; while all subsequent Index entries of the array record the **Global ID** they belong to in the same position. Amazing, isn't it? Haha 😄.

### 2. Data Entry Structure and Flag Bits

Through the above analysis, we can summarize the standard memory structure for each Index entry as follows:

| **Offset (Byte)** | **Field Name**     | **Length**  | **Parsing Description**                                      |
| ----------------- | ------------------ | ----------- | ------------------------------------------------------------ |
| `0`               | **Flag**           | 1 byte      | Variable status/type flag (see table below for details).     |
| `1` ~ `n+1`       | **String Content** | n + 1 bytes | Variable name or string content, ending with `00`. If there is no string, it is just a single `00`. *(Note: Content is encrypted via XOR 17)* |
| `n+2` ~ `n+5`     | **ID / Size**      | 4 bytes     | **Core Distinguishing Field**: If it is an independent variable or the first item of an array, this records the **Size**; if it is a subsequent element of an array, this records the **ID**. If it is a method/EXTERN, it records each parameter and local variable in the form of variables. |
| `n+6` ~ `n+9`     | **Value**          | 4 bytes     | The initial value for a signed integer. If it is a string type, this is usually padded with zeros as `00 00 00 00`. |

**Flag Bit (Byte 0) Composition Logic:**

The Flag value is actually formed by a bitwise OR combination of attributes with different weights:

| **Weight (Hex)** | **Function Category** | **Meaning Description**                                      |
| ---------------- | --------------------- | ------------------------------------------------------------ |
| `0x80`           | **Base Bit**          | Literal Entry (Mandatory identifier for Part 1 literal values) |
| `0x01`           | **Type Bit**          | Belongs to `String` (string)                                 |
| `0x02`           | **Type Bit**          | Belongs to `Int` (integer)                                   |
| `0x04`           | **Structure Bit**     | Belongs to `Array` (array `[]`)                              |
| `0x08`           | **Status Bit**        | Initialized (assigned and initialized)                       |
| `0x20`           | **Pointer Bit**       | Pointer (`*`, unused in official scripts)                    |
| `0x40`           | **(Old Ver) Status**  | Uninitialized (unassigned/uninitialized)                     |

Based on the weight combinations above, common Flag constants in decompilation are as follows:

- **Basic Unassigned:** `81` (unassigned string), `82` (unassigned int), `85` (unassigned string[]), `86` (unassigned int[])
- **Basic Assigned:** `89` (assigned string), `8A` (assigned int), `8D` (assigned string[]), `8E` (assigned int[])
- **Rare Pointer Types:** `A1` (string*), `A2` (int*), `A5` (string[]*), `A6` (int[]*)

**Old Version Flags:**

+ **Basic Unassigned:** `C1` (unassigned string), `C2` (unassigned int), `C5` (unassigned string[]), `C6` (unassigned int[])
+ **Basic Assigned:** `89` (assigned string), `8A` (assigned int), `8D` (assigned string[]), `8E` (assigned int[])
+ **Rare Pointer Types:** `E1` (unassigned string*), `E2` (unassigned int*), `E5` (unassigned string[]*), `E6` (unassigned int[]*)

### 3. Basic Variable Bytecode Parsing

To intuitively understand the structure of the Literal Table, this section will analyze the hexadecimal data of various types. Arrays have already been discussed earlier, so they are omitted here.

#### Case 1: Basic Int Variable

We define an unassigned `unusedValue` and a `gval` assigned the value of `166`:

```c++
int unusedValue;
int gval = 166;
```

The corresponding hexadecimal data in the Literal Table is as follows:

```c++
// [GlobalID: 0] Variable: int unusedValue;
// Flag | Str | Size(4 bytes)       | Value(4 bytes)
   82     00    01 00 00 00 /* Size: 1 */    00 00 00 00 /* Val: 0 */

// [GlobalID: 1] Variable: int gval = 166;
// Flag | Str | Size(4 bytes)       | Value(4 bytes)
   8A     00    01 00 00 00 /* Size: 1 */    A6 00 00 00 /* Val: 166 (0xA6) */
```

**Analysis:**

- **Flag:** `82` represents an unassigned int; `8A` represents an assigned int.
- **Str:** Because it's an integer variable, there is no string content; it just uses `00` as a placeholder and ends.
- **Size:** This is a single variable, so the Size is fixed at 1 (`01 00 00 00`).
- **Value:** `unusedValue` is filled with 0 by default; `gval`'s 166 converted to hexadecimal is `A6 00 00 00`.

#### Case 2: Basic String Variable

String handling is similar to integers, but its "value" is written directly into the `Str` field (and has undergone simple XOR 17 encryption), while the trailing `Value` field is forced to zero.

```c++
string unusedTxt; 
string txt = "sample text";
```

The corresponding hexadecimal data in the Literal Table is as follows:

```c++
// [GlobalID: 4] Variable: string unusedTxt;
// Flag | Str | Size(4 bytes)       | Value(4 bytes)
   81     00    01 00 00 00 /* Size: 1 */    00 00 00 00 /* Val: 0 */

// [GlobalID: 5] Variable: string txt = "sample text";
// Flag | Str (Encrypted String)                            | Size(4 bytes) | Value(4 bytes)
   89     64 76 7A 67 7B 72 37 63 72 6F 63 00 /* "sample text" */ 01 00 00 00 /* Size: 1 */ 00 00 00 00 /* Val: 0 */
```

**Analysis:**

- **Flag:** `81` represents an unassigned string; `89` represents an assigned string.
- **Str:** When unassigned, it is only `00`. When assigned `"sample text"`, the engine encrypts it via XOR 17 and stores it (hexadecimal `64 76...`), padding `00` at the end as the string terminator.
- **Value:** Since the data already exists in the preceding `Str` block, the subsequent Value field is uniformly padded with `00 00 00 00`.

#### Case 3: Regular Method

``` cpp
ScriptEvent4( int unit, int var1 = 114, string var2 = "text" ) {
    int val = 100;
}
```

``` cpp
// [GlobalID: 0] --------------------
// Function: ScriptEvent4( int para1, int para2, string para3 ) {
//     (Locals inside this block...)
    // [Arg 1]
    82 00                       01 00 00 00 /* Para 1 */     00 00 00 00 /* Val: 0 */
    // [Arg 2]
    8A 00                       01 00 00 00 /* Para 2 */     72 00 00 00 /* Val: 114 */
    // [Arg 3]
    89 63 72 6F 63 00  /* "text" */        01 00 00 00 /* Para 3 */     00 00 00 00 /* Val: 0 */
    82 00                       01 00 00 00 /* Para 4 */     00 00 00 00 /* Val: 0 */
```

As mentioned earlier, a method shares a single **Global ID**, which records all of its parameters and local variables.

#### Case 4: EXTERN Method

The `extern` keyword is used to declare built-in functions provided by the engine's underlying layer. In the Literal Table, `extern` functions behave very similarly to normal functions: they are also assigned an independent **Global ID**, and their parameters are recorded.

``` c++
extern MessageText(string text,int x,int y,int fontNvid = -1) 114;
```

``` c++
// Extern: MessageText (Extern ID: 114)
    81 00                       01 00 00 00 /* Size: 1 */    00 00 00 00 /* string text */
    82 00                       01 00 00 00 /* Size: 1 */    00 00 00 00 /* int x */
    82 00                       01 00 00 00 /* Size: 1 */    00 00 00 00 /* int y */
    8A 00                       01 00 00 00 /* Size: 1 */    FF FF FF FF /* int fontNvid = -1 */
```

### 4. Compiler Features

#### Feature 1: Complete Erasure of Constants

Can't find macro definitions or constants in the table? That's because the compiler directly "discards" them during the preprocessing stage and replaces them with literal numeric values.

This is quite normal; many compilers have this feature.

```c++
// Source code
#define USED_CONST 150
int constVal = USED_CONST;
```

```c++
// Compiled Literal Table: Handled directly as int constVal = 150;
// Flag | Str | Size                 | Value
   8A     00    01 00 00 00 /* Size: 1 */    96 00 00 00 /* Val: 150 */
```

#### Feature 2: Differentiated Handling of Local `Static` Variables

The logic for handling local variables inside functions is completely different depending on whether they are `static` or not, especially for arrays, which is extremely bizarre.

**If it is a `static` local variable:** It will directly retain its initialized value in the Literal Table.

```c++
static int stval = 100;
static int starr[] = {0x2222, 0x3333, 0x4444, 0x5555};
```

```c++
// Values are normally retained (64 00 00 00 is 100, 22 22 00 00 is 0x2222...)
   8A 00  01 00 00 00 /* Para 4 */   64 00 00 00 /* Val: 100 */
   8E 00  04 00 00 00 /* Para 5 */   22 22 00 00 /* Val: 8738 (0x2222) */
   // ...subsequent array elements normally carry their values
```

**If it is a non-`static` local variable:** The compiler will forcefully downgrade it to an **uninitialized variable**, and its initial values in the Literal Table are all filled with `0`. The actual assignment operation is deferred by the compiler to the later Bytecode (bytecode) execution stage!

```c++
int val = 100;
int arr[] = {0x2222, 0x3333, 0x4444, 0x5555};
```

```c++
// Flags become 82 (unassigned int) and 86 (unassigned int array), values are all 00 00 00 00!
   82 00  01 00 00 00 /* Para 9 */   00 00 00 00 /* Val: 0 */
   86 00  04 00 00 00 /* Para 10 */  00 00 00 00 /* Val: 0 */
   86 00  11 00 00 00 /* Para 11 */  00 00 00 00 /* Val: 0 */
   // ...all are 0
```

## Part 2: Symbol Table Structure Analysis

Immediately following the Literal Table is the **Symbol Table**. Its core purpose is to bind the "variable names" and "function names" defined in our source code to the `Global ID`s allocated in Part 1, and to record their metadata (such as entry offsets, parameter counts, etc.).

> **💡 Engine Trivia: Where did the local variables go?**
>
> In the Symbol Table, you will find that only **global variables** and **function names** exist. All function parameter names and local variable names are entirely discarded by the compiler! From the perspective of the engine's underlying layer, local variables are nothing more than a bunch of unnamed stack offsets and the `Index`es they occupy in the Literal Table.

### 1. Overall Symbol Table Structure

The Symbol Table starts with a 4-byte count (Entry Count), indicating how many Global ID entries there are in total in the table.

Following that is the sequentially arranged entry data. Each entry consists of a **dynamically length string** + a **fixed 24-byte attribute block**:

- **Symbol Name (String):** A string encrypted via XOR 17, ending with `00`.
- **Attribute Block (24 bytes):** A binary structure of fixed length, specifically defined as in the table below.

| **Offset (Byte)** | **Length** | **Field Name**                   | **Detailed Meaning and Processing Logic**                    |
| ----------------- | ---------- | -------------------------------- | ------------------------------------------------------------ |
| `+0`              | 2 bytes    | **Type**                         | **Symbol Type and Status Flags**. Distinguishes whether it is a variable, a regular function, or an Extern function (see the status table below for details). |
| `+2`              | 2 bytes    | **Meta / Garbage**               | **Uninitialized stack residual garbage data**                |
| `+4`              | 4 bytes    | **Extern ID / Offset / Padding** | **Core Multiplexed Field (Built-in system ID / Relative bytecode segment offset)**.<br />● **Extern Function (`Type=02`)**: Records its corresponding engine underlying system function ID.<br />● **Regular Function (`Type=03`)**: Records this function's **Relative Bytecode Offset (Relative Offset)** within Part 4 (Bytecode segment).<br />*(Formula: Physical file offset = Bytecode segment starting offset + Relative bytecode offset = actual entry address in decompiled code)*.<br />● **Global Variable (`Type=01`)**: No substantive effect, fixed padding of `00 00 00 00`. |
| `+8`              | 4 bytes    | **P1_Idx**                       | **Literal Table Index (Part 1 Index)**. Points to the starting position of this symbol's corresponding initial value in Part 1 (the Literal Table). |
| `+12`             | 4 bytes    | **Size**                         | **Size / Element Count**.<br />● **Variable**: The length of the array (e.g., 1 for `int a`, 3 for `int a[3]`).<br />● **Function**: The total length of the parameter list (**Note: Does NOT include local variables**). |
| `+16`             | 4 bytes    | **File_ID**                      | **Source File ID**.<br />● **Allocation Mechanism**: Strictly increments from `0`. `0` represents the main file, and `1, 2...` are assigned to each included file (`#include`) in the chronological order of their first physical opening during preprocessing expansion.<br />● **Gaps/Jumps Explanation**: Non-contiguous `File_ID`s (e.g., `0, 12, 13...`) often appear in the symbol table because the skipped files in between (e.g., 1~11) did not define any global variables, producing no symbol table entries and causing apparent gaps.<br />● **Note**: Only global variables have a non-zero `File_ID`; other entries are always `0`. |
| `+20`             | 4 bytes    | **Run_ID**                       | **Local Slot Index during Compilation (Run_ID)**. Has **no substantive role** during decompilation or runtime.<br />● **File Locality**: It is the independent local slot index for global variables within their respective source file (`File_ID`). Since different source files increment this independently, duplicate `Run_ID`s will occur across different files.<br />● **Non-variable Reset**: Only global variable symbols have non-zero values here; all regular functions and external functions (Extern) have this value set to `0`.<br />● **Reverse Engineering Conclusion**: The engine addresses memory entirely via the globally unique `P1_Idx` when executing bytecode. `Run_ID` is purely a compilation artifact and can be completely ignored during reverse analysis. |

------

### 2. Type Flag and "Return Value Tracking" Mechanism

The `Type` field at offset `+0` of the Symbol Table is not just used to distinguish between variables and functions; it hides a highly ingenious mechanism: **The compiler statically analyzes whether the return value of a function is actually used in the context and records this in the Type.**

**Complete List of Type Flag Enumerations:**

- **`01 00`** : Global Variable
- **`02 00`** : External Function (Extern), and return value is **unused**
- **`02 01`** : External Function (Extern), and return value is **used**
- **`03 00`** : Regular Function (Function), no return value (Void)
- **`03 01`** : Regular Function (Function), has return value, and is used by the `await` keyword
- **`03 02`** : Regular Function (Function), has return value, but is **unused**
- **`03 03`** : Regular Function (Function), has return value, and is **used**

**👇 Experimental Comparison: Extern Return Value Tracking**

Taking the extern function `CreateSprite` as an example, different calling methods will directly change its `Type` signature in the Symbol Table:

```c++
// Scenario A: Just calling it, ignoring the return value
CreateSprite(1, 10, 20, 0); 
// Corresponding Type -> 02 00 

// Scenario B: Assigning the return value to a variable
int s = CreateSprite(1, 10, 20, 0); 
// Corresponding Type -> 02 01 
```

### 3. The True Meaning of Size: The Boundary Between Parameters and Locals

For variables, `Size` is very easy to understand (it's just the array length); but for functions, the `Size` field **only counts the number of function parameters, completely ignoring internal local variables**.

**👇 Experimental Comparison: Function Size Counting Logic**

We define the following code:

```c++
ScriptEvent4( int unit, int var1 = 114, string var2 = "text" ) {
    static int stval = 100;
    static int starr[] = {0x2222, 0x3333, 0x4444, 0x5555};
    int val = 100;
    int arr[] = {0x2222, 0x3333, 0x4444, 0x5555};
}

int afterFun[] = {2, 3, 4};
```

Analyzing the compiled Symbol Table entries:

**1. Function `ScriptEvent4`:**

```c++
// Encrypted Name: ScriptEvent4
   44 74 65 7E 67 63 52 61 72 79 63 23 00 
   03 00       // Type: Function (Void - no return value)
   C9 00       // Meta 
   00 00 00 00 // Padding: 0
   14 00 00 00 // P1_Index: 20
   03 00 00 00 // Size: 3 (Core verification point: Only counts the 3 parameters unit, var1, var2)
   00 00 00 00 // FileID: 0
   00 00 00 00 // RunID: 0
```

**2. Global Variable `afterFun`:**

```c++
// Encrypted Name: afterFun
   76 71 63 72 65 51 62 79 00 
   01 00       // Type: Variable
   CA 00       // Meta: Residual garbage data
   00 00 00 00 // Padding: 0
   21 00 00 00 // P1_Index: 33
   03 00 00 00 // Size: 3 (Array length is 3)
   00 00 00 00 // FileID: 0
   1A 00 00 00 // RunID: 26
```

As you can see, although `ScriptEvent4` is internally stuffed with local variables like `stval`, `starr`, `val`, taking up a large amount of `P1_Index` space, the `Size` in the Symbol Table still displays as `03`. This confirms that the Symbol Table manages functions at the "external calling signature" level and does not care about their internal local states. However, we can still estimate the local variables inside a function by using the index difference between the adjacent upper and lower groups and combining it with `P1_Idx`.

## Part 3: Special Value Table (Action & ScriptEvent Table)

An area that defaults to being entirely padded with `FF`, used for `ActionX` and `ScriptEventX`, likely for quick positioning and map interaction.

The size and structure of this Special Value Table are **absolutely fixed**, with a total size of **2048 Bytes**. The calculation formula is: `4 bytes (size of a single slot) × 256 (supported IDs 0~255) × 2 (two groups: variables and functions)`.

If these variables or functions with special numbers are defined in the `.lgc` script, the compiler will "hollow out" the `FF FF FF FF` at the corresponding index in this area during compilation, and fill in their reference addresses.

Sample Code

``` c++
int arr[] = {1,2,3}; //id = 0 index = 0-3
int a = 114; //id = 1 index = 4

int Action2 = 100; //id = 2 index = 5
int Action5 = 200; //id = 3 index = 6

int arr2[] = {1,2,3}; //id = 4

ScriptEvent1( int val1, int val2, int val3 ){
    //id = 5
}

ScriptEvent3( int val1, int val2, int val3 ){
    //id = 6
}
```

#### Rule A: Special Variable `int ActionX`

- **Type Restriction**: Must be of `int` type.
- **Filled Content**: Records this variable's **P1_Index (Entry Index)** in the Literal Table (Part 1).
- **Example**: As shown in the code, if Action2/Action5 are defined, then the corresponding `FF` padding is hollowed out and filled with the index value.

![image-20260223184211206](./lgd_doc_EN.assets/image-20260223184211206.png)

#### Rule B: Special Function `ScriptEventX`

- **Mandatory Parameter Restriction**: Must contain **and only contain 3 parameters**, for example, `ScriptEvent5(int var1, int var2, int var3)`. If the number of parameters is incorrect, compilation will fail.
- **Filled Content**: Records this function's **Global ID** in the Literal Table.
- **Example**: As shown in the code, if ScriptEvent1/ScriptEvent3 are defined, then the corresponding `FF` padding is hollowed out and filled with the Global ID value.

![image-20260223184326996](./lgd_doc_EN.assets/image-20260223184326996.png)

## Part 4: Bytecode Segment and Instruction Set (Opcode Table)

The beginning of the code segment consists of a **4-byte integer**, representing the total length of the subsequent bytecode.

These first 4 bytes are in **plaintext** (unencrypted), but all bytecode data starting from the 5th byte is entirely encrypted via **XOR 0x25**.

### Instruction Set

#### 1. Value Types & Constants

| **Opcode** | **Mnemonic** | **Symbol** | **Description**                                | **Operands (Size & Type)**                    |
| ---------- | ------------ | ---------- | ---------------------------------------------- | --------------------------------------------- |
| `0x01`     | `PUSH_INT`   |            | Pushes an integer constant value to the stack. | **4 Bytes** (32-bit integer constant value)   |
| `0x02`     | `PUSH_STR`   |            | Pushes a string constant value to the stack.   | **Variable length** (String ending in `0x00`) |

------

#### 2. Unary Operators

*These operators act directly on the current data at the top of the stack, so the instructions themselves carry no operands (0 Bytes).*

## Call Mechanism and Special Structures

+ When the virtual machine needs to manipulate a variable (e.g., `PUSH_VAR`), it uses the variable's physical index **P1_Index** in Part 1.

+ When the virtual machine needs to call a function (e.g., `CALL_FUNC`), it uses the function's **Global ID** from the Symbol Table.

+ The engine can only call functions that have been defined prior to the call; it cannot call functions defined after it. If such a call occurs, the syntax checker will report an `Undeclared Identifier` error.

+ Every function always ends with a `RET`. They have no other meaning; they are engine placeholders used to mark the end of a function.

+ During decompilation, decompilation is performed on a block-by-block basis using the function as the smallest unit. Jumps (`JMP`) across methods are impossible, because all invocations of other methods have dedicated opcodes such as `CALL_FUNC` and `call_ext_XX`.

## Stack Mechanism and Derived Bugs

As mentioned earlier, the entire LGD script executes within the virtual machine based on a **Stack** architecture.

### Working Principle of the Virtual Machine Stack

When executing bytecode, the engine uses a Last-In, First-Out (LIFO) evaluation stack:

*   **Push (PUSH)**: When encountering constants (e.g., `PUSH_INT`) or variables (e.g., `PUSH_VAR`), the VM pushes their values onto the top of the stack.
*   **Calculate & Pop (POP)**: When encountering operators (such as arithmetic, comparison, and logical operators), the VM pops the required number of operands from the top of the stack, performs the calculation, and pushes the result back onto the stack.
    *   *For example*: To compute `a + b`, it first PUSHes `a`, then PUSHes `b`, and then encounters the `ADD` instruction, which pops both, adds them, and pushes the sum back onto the stack.
*   **Extern Calls**: When calling an Extern function, the VM sequentially pushes the parameters onto the stack, which are then popped and used by the function body all at once.

### Classic Stack-related Bugs

Since it is a stack-based VM, classic stack-related bugs inevitably occur:

1.  **Stack Underflow**: The VM attempts to execute an instruction that requires operands, but there is insufficient data in the stack (e.g., executing `ADD` when the stack is completely empty). This is rare, as the compiler usually rejects such code.
2.  **Stack Overflow**: Pushing too much data onto the stack in a short time, exceeding the maximum stack depth of the VM. This is also quite rare.
3.  **Stack Imbalance (Stack Out / Stack In)**: A hidden bug. The compilation passes, and sometimes the game even runs fine (this is even visible in official scripts). It is caused by lenient validation during compiler design.

### Stack Out Triggered by Orphaned Expressions

#### Bug Mechanism

1.  **When the `if` condition evaluates to FALSE**:
    *   It jumps directly to `loc_5573D`, pushes `0`, and executes `RET` to pop `0` and return normally. At this point, the stack is balanced.
2.  **When the `if` condition evaluates to TRUE**:
    *   It executes `PUSH_INT 1`, pushing `1` onto the top of the stack.
    *   Since there is no `else` block, the program sequentially proceeds to `loc_5573D` and executes `PUSH_INT 0` again.
    *   At this point, **both `1` and `0` coexist in the stack**!
    *   The `RET` instruction is executed immediately, and the VM pops `0` from the top of the stack as the function's return value.
    *   However, **the previously pushed `1` is forgotten and left in the stack** without being cleared.

This "forgotten 1" is the `Orphaned expression -> Stack_Out = 1` (residual stack value left by an orphaned expression) warned about by the decompiler. If this function is repeatedly called in the game's main loop, the VM's evaluation stack will eventually overflow, causing the game to crash.

### Stack In Triggered by Hanging Operators

In official scripts, you may also encounter another bug related to `#ifdef`.

This bug is even less common; it was only encountered once during testing of AS-Free 2.0.4. Unfortunately, that version did not provide source code, so we can only deduce the scenario using a simulated test script.

#### Source Code

```cpp
test_ifdef_bug_and_end()
{
    int money = 10;
    
    // If TARGET_PLATFORM_IOS is not defined
    if ( money > 100 && 
#ifdef TARGET_PLATFORM_IOS
         CheckIOSPurchase()
#endif
       )
    {
        money = 0;
    }
}
```

In a proper C++ compiler, if `TARGET_PLATFORM_IOS` is undefined, the preprocessing expansion results in `if ( money > 100 && )`, which is rejected at compile time due to the missing right operand.

However, the simple LGC compiler **successfully compiled it** and generated the following bizarre bytecode:

#### Assembly Code

```assembly
;Function test_ifdef_bug_and_end() Begin
  09DA:  01 0A 00 00 00     PUSH_INT     10
  09DF:  26 00 00 00 00     ASSIGN       test_ifdef_bug_and_end_local0
  09E4:  19 11 00 00 00     LINE_NUM     17                  
  09E9:  19 12 00 00 00     LINE_NUM     18                  
  09EE:  24 00 00 00 00     PUSH_VAR     test_ifdef_bug_and_end_local0 ; Push money (10)
  09F3:  01 64 00 00 00     PUSH_INT     100                           ; Push 100
  09F8:  0F                 GT                                         ; Evaluate money > 100 (result is false/0)
  09F9:  2C 05 00 00 00     AND_JMP      loc_09FF            ; ⚠️ Short-circuit AND: If top of stack is false, jump to loc_09FF
  09FE:  15                 LOG_AND                          ; ⚠️ Logical AND: Requires popping two operands!
loc_09FF:
  09FF:  18 13 00 00 00     JMP_FALSE    loc_0A13            ; If condition is false, skip the 'if' block
  0A04:  01 00 00 00 00     PUSH_INT     0
  0A09:  26 00 00 00 00     ASSIGN       test_ifdef_bug_and_end_local0
loc_0A13:
  0A13:  1F                 RET                              
;Function test_ifdef_bug_and_end() End
```

#### Bug Mechanism

The LGC compiler employs **Short-Circuit Evaluation** for the logical AND (`&&`):

1.  **`AND_JMP` (Opcode `2C`)**: If the left-hand condition is false (0), it immediately short-circuits and jumps to `loc_09FF`, terminating the subsequent evaluation of `&&` early.
2.  **`LOG_AND` (Opcode `15`)**: If the left-hand condition is true (1), it continues evaluating the subsequent expression and eventually calls `LOG_AND` to pop two values from the top of the stack for a logical AND.

But since the content inside the `#ifdef` block was completely hollowed out, there was no executable expression following the `&&`. Consequently, something extremely preposterous happened:

*   **Path A: When `money` is 10 (`money > 100` is FALSE)**
    1.  The `GT` result evaluates to `0` and is pushed onto the stack.
    2.  `AND_JMP` sees `0` on the stack top and **triggers the short-circuit jump**, leaping directly to `loc_09FF`!
    3.  It successfully **bypasses** the underlying `09FE: 15 LOG_AND` bytecode.
    4.  Then, `JMP_FALSE` reads `0` from the stack top and skips the `if` block.
    5.  **Result**: Because the short-circuit jump bypassed the `LOG_AND` instruction that lacked operands, the stack structure did not break, and the program miraculously executed perfectly! This is the so-called **"Stack In" lucky success state**.
*   **Path B: When `money` is set to 200 (`money > 100` is TRUE)**
    1.  The `GT` result evaluates to `1` and is pushed onto the stack.
    2.  `AND_JMP` reads `1`, **does not trigger the jump**, and the program is forced to execute sequentially.
    3.  The VM executes the next instruction: `09FE: 15 LOG_AND`.
    4.  `LOG_AND` is a binary operator that attempts to **pop two values** from the stack for a logical AND.
    5.  However, the stack contains only the computed `1` (because the subsequent expression was gutted, nothing was ever pushed onto the stack as the second value)!
    6.  **Result**: With only one operand in the stack, `LOG_AND` forces a pop, triggering a Stack Underflow, or pops unrelated data from the bottom of the stack, leading to an unpredictable crash of the VM!

The exact same logic applies to the logical OR (`||`), corresponding to the short-circuit jump `OR_JMP` and the binary operator `LOG_OR`.

### Universality of Hanging Binary Operators and Compiler Syntax Validation Rules

It is crucial to emphasize that this "hanging operator" vulnerability is by no means limited to the logical `&&` and `||` operators; it applies to all binary operators (such as `+`, `-`, `*`, `/`, `==`, `>`, `<`, etc.).

The rules are as follows:

#### Rule A: Compilation Permitted (Operator Adjacent to Parentheses)

When a hanging binary operator is adjacent to a delimiter (parentheses `(` or `)`) or nested, the compiler directly deems the syntax valid and proceeds:

Regardless of what happens, the compilation succeeds, and decompilation always produces a `stack_in` warning.

*   **Operator adjacent to a right parenthesis**: `if ( A && )` ✅
*   **Operator adjacent to a left parenthesis**: `if ( || B )` ✅
*   **Hanging in nested parentheses**: `if ( (A || B) && )` ✅

**Underlying Logic**:

The compiler's syntax tree is imperfect. It only validates the pairing of parentheses and the overall boundaries of the expression, but **completely fails to verify whether both sides of a binary operator are connected to valid sub-expressions or operands**. As long as it encounters parentheses, it assumes it has reached the boundary of the expression, completely ignoring the flaw of the hanging operator and generating the corresponding binary calculation bytecode (such as `LOG_AND`, `LOG_OR`, `ADD`, etc.) as usual.

#### Rule B: Compilation Rejected with Error (Operator Adjacent to Operator)

If two binary operators appear immediately adjacent to each other in an expression—for example, due to consecutive hanging `#ifdef` blocks—the compiler will directly throw an error:

*   **Different adjacent operators**: `if ( A && || B )` ❌
*   **Identical adjacent operators**: `if ( A && && )` ❌

**Underlying Logic**:

This is because during the lexical analysis (Lexing) or basic token stream validation stage, the compiler enforces an ironclad rule: "The next non-empty token after a binary operator must never be another binary operator." When two binary operators appear consecutively, the compiler cannot even generate a basic syntax tree and directly throws an `Undeclared Identifier` or lexical parsing error.
